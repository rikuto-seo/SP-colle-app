# SP Colle PR #1 最終レビュー・性能検証

対象：`fix/stats-photo-completion` / PR #1。2026年10月25日実施。
本番DB接続・元マスター変更・対応表変更・マイグレーション・デプロイ・mainへのマージは実施していません。

## 1. 発見した問題

1. 同一グループの同名メンバーでは、`member_stats`が名前で合算され、`comp_stats`は後のメンバーに上書きされていました。ランキングの表示名では区別できず、名前指定の詳細APIも複数人分を混在させていました。
2. 統計は全Photoの行と集合をPythonに展開していました。10万件では統計の中央値が約1.63秒、Python割当ピークが約63MiBでした。
3. 共有統計は全Photoを再取得して一括描画していました。10万件で約4.07秒、約59.8MBのHTML、Python割当ピーク約278MiBでした。
4. 追加ページの名前による検索では、同名メンバー・同名衣装で複数Photoが一致すると、先頭のPhotoを選んで更新する経路がありました。

## 2. 修正内容

- メンバー別所持数・コンプ・ランキング・未所持の内部識別をメンバーIDに統一。表示名は元のままです。
- 詳細取得は`/stats/member/<group>/id/<member_id>`を使用。対象グループ外・存在しないIDは404。既存の名前URLは一意な場合のみ許可し、同名なら409で混在を防ぎます。
- 未所持リストもIDでまとめ、検索フォームを`member_id`・`costume_id`で絞り込むようにしました。統計全体の再集計は不要になりました。
- DB側でPhoto数・正の所持数・実数量を集計し、種類の分類解決も衣装ID×PhotoType IDの集約後に行います。Photo単位の判定、4分類、未分類別集計は維持しています。
- 共有統計はPhoto ID順に100件ずつ表示。総数・所持枚数・分類集計は現在ページではなく全件を対象とします。公開／非公開の判定は先に行います。
- 追加操作は候補が曖昧なら409で停止し、任意のPhotoを更新しません。元ラベルに加えて`member_id`・`costume_id`を渡せば一意に指定できます。不正なID入力は400です。
- 新しい分類推測・複雑なキャッシュは追加していません。

## 3. 性能テスト結果

### 条件と測定方法

- 写真数は正確に10,000・50,000・100,000件。メンバー50人、衣装ごとに最大6種類、数値表記と装飾名、未分類文字列を含む合成データです。
- 所持行は全Photoの70%で、そのうち正の数量が60%、0枚が10%。正の数量は1～4枚です。数字の衣装別分類は合成DBに明示設定しました。
- 本番DBは使わず、一時ディレクトリのSQLiteへ作成。テストアクションごとに新しい子プロセスを使います。作成処理は測定対象外です。
- 各アクションでテンプレート・SQLコンパイルを1回ウォームアップし、その後3回計測。以下は中央値と最大値で、ネットワーク往復・CDN・ブラウザ描画は含みません。P95や同時アクセスの測定ではありません。
- 統計と共有統計はFlaskテストクライアントによるページHTML生成までの応答時間。メンバー別コンプはサービス呼出しとJSON化の処理時間で、対象はグループ内の1メンバーです。修正後はID指定です。
- 時間計測時は`tracemalloc`を停止し、Python割当ピークを別の1回で取得しています。RSSは子プロセス全体のピークで、起動・ウォームアップ・割当計測器の負荷を含みます。Python割当量とRSSは同じ指標ではありません。
- DB回数はSQLAlchemyイベントで各計測中のSQL実行を数えています。規模が増えても回数は一定です。IDの所属確認・ページ分割のCOUNT追加により回数は少し増えますが、転送量とメモリは減ります。
- 環境：Windows 11、Python 3.12.10、SQLite 3.49.1、Flask 3.1.0、SQLAlchemy 2.0.40。単一ローカル環境での比較であり、PostgreSQL本番の応答時間を保証しません。
- 修正前は`d73b17fa53a205270a2619af8c7089b71d5a878c`。修正後は本PRのSQL集計・ID識別・100件ページ分割を含むコードです。

各行の括弧内は修正前の値です。時間はms、メモリはMiB、SQLは1操作の実行回数です。

- **メンバー別コンプ処理**：中央値 **5.56**（17.63）、最大 6.17。SQL **4**（3）回。Python割当ピーク **0.28**（0.83）、プロセスRSSピーク **76.48**（78.75）。

生の3回分の時間、クエリ回数、メモリ、応答サイズは`docs/stats-performance-results.json`に保存しています。再実行方法：

```text

```

`DATABASE_URL`を接続先に使用せず、常に合成SQLiteを使うハーネスです。

## 6. 残る懸念事項

- PostgreSQL、実DBの偏り、並行アクセス、ネットワーク・ブラウザ描画の負荷は未測定です。本測定は単一ローカルSQLite・3回の中央値です。
- 共有統計の写真描画は100件で制限しましたが、未分類の一覧行やメンバー×衣装の集計結果は依然としてデータ量に応じて増えます。今回の10万件では問題は再現しませんでしたが、将来のさらに大きいデータには別途評価が必要です。
- 追加フォームの選択値は従来どおり名前です。同名候補を画面上でID選択する拡張は未実装で、曖昧な追加は409で停止します。ID指定可能な呼出しは正しいPhotoを更新できます。既存の一意な名前の追加はブラウザ・自動テストで確認済みです。
- 実DBの対応漏れ、永続的な未分類管理一覧、取込時の対応漏れ検知、曖昧表記の扱いは既定の後続課題です。
- GitHub上のレビュー承認や本番への適用可否は別の判断です。CIの状態とドラフト状態はPRで確認してください。
