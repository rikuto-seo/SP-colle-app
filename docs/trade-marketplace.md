# トレード募集と取引管理

入口は `/trade/<group_key>`。共通ヘッダー・メニュー・スマホの下部ナビから移動できます。

一覧は提供写真を中心に、その下に「⇄ 求」と希望写真を添えたギャラリー。スマホ2列、タブレット3列、広い画面4列で、新着・郵送・現地・セットとメンバーから閲覧できる。細かい検索は「絞り込み」を開く。検索に一致した写真をカードの代表として表示し、複数種類の条件や枚数の詳細は募集ページで確認する。実物画像がない場合はメンバー名とカットを表示する。実物画像は縦長の比率を保持し、切り抜かない。

「もっと見る」は一覧に次の20件を追加する。JavaScriptが無効な場合も通常のリンクとページ番号で閲覧できる。この一覧変更に追加のDBマイグレーションは不要。

## 使い方

1. 「募集を作る」で所持写真と枚数を選ぶ。
2. 提供写真ごとに希望写真・必要枚数・希望度を登録する。「いずれか一つ」と「すべて必要」は提供写真1枚あたりの条件。
3. コンプを崩さず交換する場合は「一式でセット交換」を選ぶ。提供一式と、全欄に追加した希望写真一式を交換する。同じ希望写真が複数欄にある場合は最大の指定枚数をセット全体の枚数とする。
4. 下書きを保存し、公開される写真・表示名・条件を確認して公開する。画像はチェックを入れた写真の先頭画像のみ公開する。
5. 「欲しい写真を出している募集」と「自分が渡せる写真を求めている募集」の両方向から、メンバー・衣装・カットを指定して検索する。
6. 募集の詳細から写真と枚数、方法を選んで交換案を送る。相談と画像共有は当事者だけに表示される。
7. 募集者の承認で双方の在庫を取り置きする。発送・受取をそれぞれ連絡し、双方の受取確認で所持数と通常の希望リストを一度だけ更新する。

下書き・停止中の募集は募集者だけに表示。募集を停止しても確定済みの取引は続けられる。確定後のキャンセルは双方の合意が必要で、受取確認後は取り消せない。写真・枚数を変更する場合は提案を取り消し、新しい提案を送る。

取引完了で所持数が0になっても、元の所持レコードとアップロード画像は保管する。画像ファイルの所有者を移したり、R2のファイルを削除したりしない。受け取った写真は受取側の所持レコードに加算する。

## 公開範囲

募集の公開状態は `trade_listings.status`。公開検索・共有に表示するのは、募集用の表示名、選択した提供写真・希望条件・交換方法・場所・注意事項。メール、SNS、コレクション全体を取得して表示しない。

従来のコレクション共有は `want_shares.is_public`、欲しい写真リストの共有は `want_shares.want_public` に分離。移行時は従来の公開状態を引き継ぎ、その後は独立して切り替える。新しい募集を公開しても、この2つのフラグは変わらない。

メンバー単位の無限回収は `want_members` に保存する。従来の写真単位の無限回収も保持する。

## QR交換チェック

サイドバーの「QR交換チェック」から `/trade/qr/<group_key>` を開く。カメラ、保存したQR画像、共有URLの入力から、従来の「提供可能な写真」と「欲しい写真」を照合できる。募集・取引とは別の機能で、照合だけでは募集作成・交換確定・所持数更新を行わない。

欲しい写真リストのQRと従来の所持一覧QRに対応する。所持一覧QRを使う場合も、相手の欲しい写真リストの公開が必要。自分の希望リストを公開する必要はない。QRから読み取ったグループで判定し、提供可能枚数から確定済み取引の取り置きも除外する。カメラは利用者がボタンを押して起動し、読み取り後・終了時・ページ離脱時には停止する。画像はブラウザー内で読み取り、サーバーには共有URLのみを送る。

QRデコーダーはローカル同梱のjsQR 1.4.0（Apache-2.0）。出典とライセンスは `static/js/vendor/` に保管。カメラが使えない環境でも画像・URLから判定できる。DB変更は不要。

```powershell
& myenv/Scripts/python.exe -B -X utf8 -m unittest discover -s tests -p test_qr_check.py
& myenv/Scripts/python.exe -B -X utf8 tests/check_qr_browser.py
```

ブラウザテストはサンプルの実QR画像・模擬カメラ映像をメモリ内で作成して検証する。スクリーンショットは保存しない。

## DBの反映

追加マイグレーションは `d8f1c3a6e902`（親は `c4e8a7b91d26`）。既存の写真・所持数・ユーザーは変更しない。既存ユーザーの募集を自動で公開しない。

本番で新しいコードを起動する前に、既存の設定済み環境で以下を実行する。

```sh
python -m flask --app app db upgrade
```

2026年10月12日、現在のローカル設定で接続するPostgreSQLへ `d8f1c3a6e902` を適用済み。既存のユーザー数・写真数・所持レコード数・所持枚数と公開設定の引き継ぎを確認した。アプリのデプロイは実行していない。

適用状況は `python -m flask --app app db current` で確認できる。デプロイ先が別のDBを使用する場合は、その環境でも起動前に `db upgrade` を実行する。

## 検証

```powershell
& myenv/Scripts/python.exe -X utf8 -m unittest discover -s tests -p 'test_trade*.py'
python -X utf8 -m unittest discover -s tests -p test_design_templates.py
node --check static/js/trade.js
```

テストは `app.py` や `.env` を読み込まず、SQLiteの一時DBで行う。PostgreSQLでは、在庫を書き換える操作と承認・完了処理が同じユーザー行を一定順序でロックする。取り置き分を従来の減数・削除画面から消せないことも検証する。

ブラウザの実操作確認には、別ターミナルで以下のテスト専用サーバーを起動する。このサーバーはlocalhostとメモリ内DBだけを使用する。

```powershell
& myenv/Scripts/python.exe -X utf8 tests/serve_trade_fixture.py
python -X utf8 tests/check_trade_browser.py --browser "$env:LOCALAPPDATA/ms-playwright/chromium-1208/chrome-win64/chrome.exe"
```

ブラウザテストはPlaywrightとChromiumが必要。生成画像は `%TEMP%/spcolle-trade-marketplace` に保存する。Firebase・Stripe・実際の相手への連絡は呼び出さない。
